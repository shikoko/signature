# Working on the Gmail Signature Builder

A static site with no build step. The **Website** workflow (`.github/workflows/website.yml`) publishes `main` to https://shikoko.github.io/signature/ on every merge. It publishes only `index.html`, `styles.css`, `signature.js`, `app.js`, `assets/` and `icons/`, so a new file the page needs goes on that list.

- `index.html`, `styles.css`: the page
- `signature.js`: the signature's details and the renderer for the copied HTML, the email preview and the editable card
- `app.js`: editing, the hover bar, the pop-ups, the Layout panel and copying
- `icons/v1/`: the icons copied signatures link to; `tools/icons/` draws them
- `assets/`: favicon, example photo, social preview image

## Commits and pull requests

- **No attribution lines, anywhere.** No "Co-Authored-By: Claude", "Claude-Session:", "Generated with Claude Code", "Generated by Claude Code" or similar, in commit messages, pull request titles or descriptions, or comments. `.claude/settings.json` turns off the ones Claude Code adds by itself.
- **Always remove the "Generated by Claude Code" footer.** A pull request, issue or comment written or edited from a Claude Code cloud session gets "_Generated by [Claude Code](…)_" added to its end (a description gets a `---` line above it too), and it comes back after every edit made from there. The **Tidy footers** workflow (`.github/workflows/tidy-footers.yml`) removes it within a minute from the owner's pull requests, issues, comments and review comments. After writing or editing any of them, check that the footer is gone; if it isn't (the workflow didn't run), remove it from a session that can edit it without the footer coming back, or ask the maintainer to.
- **Commits are the maintainer's.** Author and committer are the repository's owner, never Claude, and commits from a cloud session aren't signed with the session's key.
- **Branches:** make a branch from `main` for each change and open a pull request into `main`. Nothing is pushed to `main` directly.
- **Every pull request is merged with a merge commit:** never "Squash and merge" or "Rebase and merge", which copy the commits and leave the branch looking unmerged in the graph.
- **Rebase before merging:** before merging a pull request, rebase its branch onto the latest `main` and push it (`--force-with-lease`), so the branch starts from the tip of `main` and the graph shows a short loop that joins straight back in.

## Writing commit messages and pull request descriptions

Commits go out under the maintainer's name and are public, so they get quoted out of context. Write them as an experienced engineer would.

- **Only facts about the change.** Plain technical terms: what changed and why. No commentary or chatty asides, and nothing that sounds unsure.
- **Every sentence should read well quoted on its own.**
- **Mention side effects** (regenerated images, changed defaults, new outside services) in a final line or bullet.
- **British spelling**, as on the rest of the site: colour, licence.

### Commit messages

- **Subject:** imperative, specific, under 72 characters: "Warn when the photo link doesn't load", not "Photo improvements".
- **Body:** what changed and why, wrapped at 72 columns. Name the files, settings or behaviour that changed.

### Pull request descriptions

- **Start with the problem** in one or two sentences: what was wrong or missing, as someone using the page would see it.
- **Changes:** a short list of what the pull request does, naming files, settings and behaviour.
- **Tested:** what was checked (the page in a browser, light and dark, at phone width; pasting into Gmail) and the results, and what couldn't be tested, with the reason.
- **Screenshots** for anything you can see on the page.
- Refer to design options by what they are, not only by a letter from a conversation ("the edit-in-place layout", not just "option C").

## The page

- **The signature it copies** is tables and inline styles, in one of the fonts in `FONTS` in `signature.js`, because Gmail removes stylesheets, web fonts, SVG and `data:` images from signatures. A font added there must come with Windows, macOS and iOS, and its list must end in a generic family (`sans-serif` or `serif`). Images in it (the photo, icons) are hosted PNG or JPEG files. Keep it under Gmail's 10,000-character limit.
- **Never change, move or delete a file in `icons/v1/`.** Signatures pasted into people's mail keep loading those exact addresses. New icons are new files; new artwork for an existing icon goes into `icons/v2/`. See `icons/README.md`. `.github/scripts/check-icons.mjs` checks this on every pull request and before every deploy, and the site isn't published while it fails.
- **One renderer.** The copied HTML, the email preview and the editable card all come from `render()` in `signature.js`, so a change to how the signature looks is made there once.
- **Alignment is checked, not eyeballed.** Icons next to text sit on the text's centre line (see `icon()` in `signature.js`); controls are fixed-height flex boxes. After a visual change, measure text and icon centres in the controls and in the signature across layouts, and check that nothing is clipped.
- **Words on the page** are plain and friendly: say what happens. Errors say what went wrong and what to do about it.
- **Example data** uses made-up people: names that aren't real, `example.com` addresses, and UK phone numbers from Ofcom's drama range (`020 7946 0000` to `0999`).
- **Nothing is sent anywhere.** Details stay in the browser's `localStorage`. If a change talks to a new service, say so in the pull request.

## Checks

- Published icons unchanged: `node .github/scripts/check-icons.mjs` (needs the full history).
- The footer script's tests: `node --test .github/scripts/tidy-footers.test.mjs`
- The **Checks** workflow (`.github/workflows/checks.yml`) runs both on every pull request.
- Open `index.html` through a local server (`python3 -m http.server 8000`) and check the page in light and dark, at desktop and phone width, with no errors in the console.
